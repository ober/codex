# FreeBSD Jerboa MCP tool inventory

This file is a sanitized inventory of the live Jerboa `tools/list` schema queried on the native FreeBSD host. It distinguishes provider-level calls from Codex dispatch. The configured server originally reported `readOnlyHint=false` and `idempotentHint=false` for every tool, so the risk classes below are conservative name/description/schema-based triage, not trusted MCP annotations.

The configured server schema contained 51 tools. Final end-to-end tests used the patched native FreeBSD provider source commit `69c6992b531ac213c7e0332708832c2cd50ae2e1` (version 0.13.23) from its versioned side-by-side package with the latest installed Codex pair (CLI SHA-256 `b9743a5866103e6a6aab345c9fe819cece5f2f7d5c2652d8194f1dc292891cc8`, helper SHA-256 `b597ca4355045a6b7fed78714266db21c637a69c865ab5ab42004574220deadf`). The executable reported runtime 0.13.23, protocol 2025-03-26, and 51 tools. `scripts/freebsd/test_code_mode_appserver.py --case jerboa-all` passed 60 actual native Code Mode MCP calls across all 51 unique names. The direct-provider fixtures separately passed the six knowledge writer APIs with write/readback under temporary data roots, and all 45 nonwriter names. No user knowledge store was used in those fixture runs. No response payloads or credentials are included. ## Side-by-side installed provider and production-root smoke

The patched provider was staged under
`$HOME/.local/lib/jerboa-mcp-freebsd/69c6992b531ac213c7e0332708832c2cd50ae2e1/`
as a self-contained package (37,501 KiB allocated). It contains the native
FreeBSD `jmcp`, its matching `bin/jerboa`, Chez runtime, libraries, and license
notices; its symlinks stay within the package. Native `ldd` resolved all
dependencies for `jmcp` and the Scheme runtime. The staged `jmcp` SHA-256 is
`9d2602136b0ce71cd1a34bb6193ce0f86e36f8d034019f904a55443751580faf` (version
0.13.23).

The installed native Codex scratch replay passed all 60 calls / 51 methods
against this staged package, with writer arguments rooted in the harness's
temporary fixture. The active MCP config now selects that versioned `jmcp`
and supplies its matching `JERBOA_HOME` and `JERBOA_MCP_JERBOA_PATH`; the
existing `JERBOA_MCP_DATA_DIR` and `JERBOA_MCP_REPO` values were preserved.
The old `~/.local/bin/jerboa` and `~/.local/bin/jmcp` were not replaced. A
configured native Codex read-only `jerboa_list_features` smoke completed four
distinct correlated call IDs; every call reached terminal `completed` with a
nonempty result. Two returned one entry for `limit=1`, and two returned no
matching entries. The production catalog SHA-256 was identical before and
after the smoke (`fec1ae604d962d41bf1b90ea300e0cede6119676f88a3d622d328a89e190e9c9`),
so the configured read did not mutate it. The formatter regression test
verifies list-valued and string-valued `implemented_in` output and checks that
unsupported value types return a typed, sanitized MCP error. The scoped config
backup is `~/.codex/config.toml.backup-jerboa-mcp-20261017T014929Z` (mode
0600); only the Jerboa command and matching runtime paths changed.

The direct-provider fixture `scripts/freebsd/test_jerboa_nonwriters.py`
completed 49 calls across all 45 nonwriter names in temporary project/data
roots. Three calls were deliberate negative validation probes; every method
also had a successful result. Both `echo-args` (`scratch-ok`) and `count-args`

stub; no external model endpoint or paid service was used. The separate
native Code Mode replay used a local model stub and passed all 60 calls across
all 51 live schema names, including the six knowledge-writer families, with
